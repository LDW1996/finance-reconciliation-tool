# 邮件收款匹配

入口为工具顶部“邮件收款”。默认进入收款匹配；“邮箱与邮件”用于配置自动读取、查看原文和导入验证邮件。

## 日常自动读取

1. 在 Windows 打开经典版 Outlook，以同一用户、相同权限登录。工具通过 Outlook COM 读取已配置邮箱，不另存邮箱密码；新版 Outlook 不适用此连接方式。
2. 连接 Outlook 后选择邮箱和文件夹，设置历史天数（默认 90 天）、每批数量和检查间隔，开启自动读取。
3. 首次按固定时间窗口分批补扫，后台继续下一批；完成后按水位增量读取，并重叠一天去重。进度持久保存，重新补扫可重置窗口。单封失败会显示原因，不保证无法读取的邮件已完整采集。
4. 勾选“启动后恢复自动读取”后，Windows 下重启工具会恢复配置。保持用户登录、工具运行且 Outlook 可收信；关闭浏览器不会停止后台，退出工具会停止。公司权限弹窗须在 Outlook 中处理。
5. 图片及 PDF 自动进入本地识别队列，再进入付款候选索引；中断的识别任务重启后恢复。不会设置已读、移动、发送或删除邮件，也不执行附件链接。

## 流水匹配和复核

- 推荐使用“配置在线来源”：填写目标 Google Sheets 工作表完整链接（含 gid），选择 Google 服务账号 JSON。授权文件加密存于本机，不需财务每次输入。管理员需在 Google Cloud 启用 Sheets API，创建服务账号密钥，并将目标表以编辑权限共享给界面显示的服务账号邮箱。当前会话中的插件授权不会自动进入交付程序。请勿将密钥放入代码或安装包。
- 点击“读取在线流水”获取最新快照。邮件识别及候选匹配仍在本地完成；在线流水读取和回写由用户触发，本版本不定时自动写入。也可继续导入本地文件验证。
- “回写已确认关联”处理当前在线流水全部已确认关联（包括其他页面及筛选范围），确认弹窗显示总数。只更新专用邮件备注、分数和检索信息；已有人填写且不能确认是本工具写入的内容不覆盖。缺失或重复参考号、日期/金额/付款人/描述/状态变化会跳过并记录。
- 回写按参考号重新定位，提交前重新读取、提交后回读验证；重复回写内容一致时不发送修改。Google Sheets 不提供此流程所需的行级条件写入，最终提交瞬间的多人并发修改仍有风险，回写期间请勿排序、插入、删除或编辑目标行。超时不盲目重试，先读取对照；无法确认的请求保留待核实状态。
- “同步记录”展示最近 200 条本地记录，可展开修改前后内容。每次写入先持久保存快照，再调用 Google；包含时间、表及工作表、流水参考号、行号、结果和原因。默认长期保留，不受清空邮件缓存影响；历史快照行号仅作记录，下次不据此直接写入。仅能写回当前已读取且配置一致的在线表，本地文件不会直接写到在线表。

- 导入 XLSX、XLS 或 CSV，选择币种；优先识别 Bank Transactions 工作表，可指定其他工作表。默认筛选未识别流水，可切换未核销或全部。样例中已 CLOSED 的流水需切换“全部”。
- 按付款金额、付款日期、付款人匹配：金额最多 50 分、日期最多 20 分、付款人最多 30 分。金额和币种是评分项：金额差异允许保留（需付款人相似且日期合规）；币种冲突不排除，但金额项计 0 分并提示核对，不自动换汇；付款日期缺失时使用邮件时间代用，并明确标注来源。匹配日期必须落在页面设置的前后日期窗口内，两种日期都不可用时不匹配。默认日期窗口前后 3 天，可调整。分数是规则相似度，不是付款真实性或核销概率。
- 每笔默认显示前三个付款证据候选，可展开更多。同一邮件可能有多个付款附件；相同证据的来源邮件保留检索信息，不叠加得分。
- 不把发件人当付款人；优先明确付款日期，缺失时以邮件时间作为匹配日期（并非凭证付款日期），旧索引读取时同样应用，无需重新 OCR。多个不明确字段保留警告。提单号、发票号等用于丰富备注，不替代三个付款要素。
- 人工确认、暂不关联或恢复待核对仅保存本地关联。选定证据变化会要求重新核对；不修改银行流水核销状态，不触发 iLog。
- 导出新 XLSX，在流水右侧添加候选备注、匹配分数、邮件检索信息。检索信息包含关键词、实际主题、发件人和邮件时间。未确认候选标记待核对，原文件不覆盖。XLSX 保留原有工作表；XLS/CSV 转为选定表的 XLSX，不保证保留原格式和其他工作表。

## 手工验证与识别边界

Mac 可导入 MSG/EML，验证相同的识别和匹配流程；真实 Outlook 自动接入须在 Windows 财务电脑验证。导入按纯文本显示，不执行邮件 HTML 或脚本。

图片使用随包分发的 RapidOCR ONNX 本地模型，关闭推理遥测；PDF 文字页提取文字，扫描页渲染识别，不调用在线 OCR。结果保留页码、原文和预览。OCR 可能误认字符、丢空格，置信度不等于匹配分。

上限：邮件 25 MB、每封最多 20 个附件、单附件 10 MB、每次读取附件累计 100 MB；PDF 前 10 页、图片 1200 万像素、多帧只读首帧。达到上限会提示。流水最多 25 MB、2 万行，无法解析日期或金额的行会跳过并计数。邮件列表每页显示 50 封，可翻页与全库搜索；保存总数与扫描数量分开显示，付款索引使用全部已识别邮件。

正文、附件、读取进度、付款索引及流水关联在本机加密保存，密钥与数据库同机，不防御已能访问该用户文件的人。记录默认保留；清空邮件缓存不删 Outlook 原件，也不等于删除已导入流水。所有邮件接口校验本机来源。

## 验证与交付

自动测试覆盖模拟 Outlook 分批读取、持久进度、字段解析、匹配、人工关联及导出，不连接真实邮箱或执行解锁。Windows 打包配置包含 OCR 模型和 PDFium。真实 Outlook 权限、公司策略、收信同步和冻结程序仍需在 Windows 验收。

### 附件识别并发

附件识别默认上限为 4 路，使用独立进程，每路 OCR 使用 1 个计算线程；数据库仍由主进程保存。实际并发在管理器初始化时取以下最小值：4、逻辑 CPU 核心数的一半（向下取整）、可用物理内存扣除 2 GiB 后每 1 GiB 一路，最低为 1 路。Windows/Linux 支持读取可用内存；无法读取时保守使用 1 路。要跑满四路，需要至少 8 个逻辑核心、当时至少 6 GiB 可用物理内存。这是保守的启动预算，不是硬内存限制，也不是运行期间动态降载；大型扫描件及其他程序仍可能造成内存压力。

启动前可设置环境变量 `FINANCE_OCR_WORKERS=1` 或 `2` 降低上限，重启程序生效。队列排空后识别进程退出。进程异常或内存异常时暂停新任务，未完成邮件仍在持久队列中，可重新识别或重启恢复，不将全部积压误标为附件损坏。单个坏附件仍记录失败并继续其他附件。`/api/mail/status` 返回 `analysis_workers`（实际并发上限）和 `analysis_active`（正在处理的邮件数）。

自动测试包含四个真实 spawned OCR 进程、金额/日期识别、并发上限、重复入队、坏附件及进程异常恢复。Windows 冻结程序已接入 `freeze_support()`；发布前仍须在目标 Windows 电脑运行成品冒烟测试，确认子进程启动及实际资源占用。

金额差异评分：同币种且金额完全一致 50 分；相对差额（按两者绝对值较大者为分母）不超过 1% / 5% / 10% 分别为 35 / 25 / 15 分，其余 0 分。金额不同时付款人至少达到近似匹配（名称相似度 0.8）才保留；币种缺失或冲突金额项为 0 分。付款人最多 30 分，日期最多 20 分；日期必须在页面窗口内。候选仍需人工确认。

### 升级保留和断点恢复边界

本次四路并发不修改数据目录、加密方式或既有表字段。同一 Windows 用户、相同数据目录下，沿用 `mail/mail.sqlite3` 与 `mail/mail.key`；原邮件、附件、已保存的 OCR 结果、流水和人工确认记录保留。启动只恢复队列中的任务及待识别/识别中附件，已完成附件不重做 OCR。恢复以附件为单位：被中断且结果尚未保存的附件会从该附件开头重做，不支持在 PDF 某页或 OCR 某一步继续。原识别失败附件不会因为升级而自动重试。

Outlook 的读取范围和分页游标保存在原库中，相同范围继续读取会使用原断点；保存邮件后、提交游标前若中断，可能重读上一批，原有去重逻辑保留已有结果。调整邮箱/目录/日期范围或主动重新补扫会改变读取计划。未勾选“启动后恢复自动读取”时，需要重新开启读取；本地未完成附件的恢复不依赖该开关。

正式升级先退出旧程序，备份整个 `%LOCALAPPDATA%\FinanceReconciliation` 目录（使用自定义 `FINANCE_RECONCILE_DATA_DIR` 时以该目录为准），再启动新版。不能同时运行新旧版，不能只复制数据库而遗漏密钥。该备份是目标电脑升级操作，源码修改和本地自动测试不会替目标电脑创建备份。缺少原密钥时程序拒绝打开旧库，不会生成替代密钥覆盖旧数据。

`test_mail_upgrade_resume.py` 验证旧队列 claimed 状态恢复、完成附件跳过、未入队待识别附件补入队、已完成加密数据/确认记录/流水/密钥不变、二次启动不重做识别及密钥缺失时拒绝打开。目标 Windows 安装包升级仍需在旧数据备份副本上验收。

### 重复附件复用与文字 PDF 提速

- 按附件原始字节的 SHA256、图片/PDF 解析类型及识别规则版本复用成功结果。文件名不同但内容相同可复用；文件内容、解析类型或已知版本不同则重新识别。同一管理器内即使四路同时遇到同一附件，也只进行一次有效识别。识别失败、没有页面或含页面失败提示的部分结果不作为可复用结果；失败副本仍可重试。
- 新增 `mail_recognition_lookup` 是可重建的结果引用索引，不复制缓存预览、不保存明文识别内容。原附件结果继续加密存储；每次命中都验证源附件仍已完成、内容指纹及版本仍匹配。每封邮件仍有自己的附件、付款条目和证据 ID，不合并人工确认。重启后可复用；清空本地邮件时同时清除此索引。
- 升级后的第一次识别会在后台按当前版本扫描旧附件元数据，索引兼容的旧成功结果；这是一次性开销，不重新 OCR、不改写原完成附件。后续版本若不兼容会隔离旧缓存。已有旧邮件、确认记录和读取断点仍沿用。
- PDF 先提取文字。文字充足且没有图片时直接解析文字；带小图片的页面还要求原生文字中有付款人、金额、日期，并对小图区域做文字检查。任何小图文字或检查异常都会回退整页 OCR，防止漏掉图片中的金额更正。大图、文字不足、乱码、旋转或不确定坐标的图片页保守走原 OCR 路径。确认为无文字的小图判定按像素指纹在单个进程内复用，最多 128 条，不保留像素副本。
- 纯文字页只渲染到预览需要的尺寸（最长边受 1200×1600 范围约束，最多 2 倍），扫描页仍保留原有渲染上限。未修改历史识别结果，也不降低扫描件的 OCR 分辨率。实际收益取决于重复附件和原生文字 PDF 的比例；Windows 成品速度及升级仍需目标电脑验收。

### 可测量的读取提速与恢复

- 读取前检查同一邮件 ID 的二进制 Outlook 变更标识（[PidTagChangeKey](https://learn.microsoft.com/en-us/openspecs/exchange_server_protocols/ms-oxprops/e9ad95c1-83b7-4ee8-9d72-60f8faffc0d2)）。仅当原读取完整、标识仍相同且读取规则版本兼容时，跳过正文读取和附件下载；缺失标识、不支持该属性的 PST、旧数据没有标识、附件曾下载失败/超限、正文截断或捕获中标识发生变化，都走原读取流程。OCR 失败的重试仍按原人工重试规则处理，不由下载跳过逻辑自动重做。
- 跳过的是重复的下载工作，不会删除邮件或重新写入已完成结果。即使一整批均未变化，扫描计数和原分页游标仍推进；界面“读取”包含检查过但未变化的邮件，“新增”只统计新保存邮件。
- 识别积压达到队列上限时暂停读取；积压（含在处理邮件）降到上限的一半后，开启自动读取的任务会安排 1 秒后继续，沿用原范围和断点。停用自动读取后旧回调失效；磁盘不足和识别异常时不会触发快速恢复。仍保留原定时检查作为后续重试。
- 处理速度与耗时面板统计本次启动：最近约 60 秒处理附件数、OCR/文字 PDF 页数、复用次数、未变邮件跳过数、读取与附件下载耗时、附件分析处理耗时、保存/入队耗时、去重等待。运行中的识别处理数量不包含等待相同附件结果的任务。读取耗时包含附件下载，分析耗时包含 PDF/预览及进程启动等待，各路累计时间会重叠，不能相加当作总耗时。最近窗口按秒聚合，边界误差不超过 1 秒，内存占用有上限；重启后清零。
- 性能 JSON 仅含构建版本、导出时间和以上统计，不含邮件正文、目录地址、附件内容或密钥。正式成品冒烟测试验证真实离线 OCR、相同附件不重复分析、重启后完成结果与密钥不变；不连接真实 Outlook。

### 识别故障诊断与有限自动恢复

单封邮件内容/付款整理异常记录失败并继续其余邮件，保留已完成附件与付款证据。SQLite BUSY/LOCKED 最多额外恢复 3 次，间隔 1、2、4 秒；识别进程池退出同样最多重建 3 次，旧进程池和控制线程收尾后才创建新池。未确认完成的任务保持在原持久队列，重试先恢复领取状态，再跳过已经完成的附件。自动轮询不会重置已经耗尽的恢复预算，须在处理故障后手动重试；程序重启属于一次新的恢复运行。

SQLite FULL、CORRUPT、NOTADB、READONLY、IOERR、磁盘 ENOSPC/Windows 磁盘满、权限异常和 MemoryError 不盲目重试。界面分别显示原因、发生阶段、异常类型/错误码、已使用的恢复次数和建议操作，并暂缓新增读取。内存中的最新诊断和最近 20 项故障可随性能 JSON 导出，不含原始异常文本、邮件标识、正文、路径或密钥。`mail-errors.log` 位于邮件数据目录，单文件最多 256 KiB、保留两份轮转；写日志失败不覆盖原始故障提示。

状态查询遇到数据库异常时返回最近成功计数和明确的状态读取诊断，避免故障提示本身被查询失败遮住。存储占用接口返回分类后的原因；前端区别后台错误、连接失败与 30 秒查询超时，并且状态接口失败不会遮盖存储查询的实际错误。日志和当前统计在旧版程序中不存在，升级后才能定位新的故障；不能据旧截图回推确定昨晚的根因。

### 邮件存储优化（兼容旧库）

- 新附件原件按原始字节 SHA256 共用加密存储，邮件各自的附件 ID、来源、OCR 文字、付款索引和人工确认保留。不修改 Outlook/PST，也不合并付款记录。
- OCR 不再生成长期预览图片。查看原件时按页生成，独立加密缓存默认上限 256 MB（32–2048 MB 可配），按最近使用及 7 天过期规则淘汰；预览缓存可重建。
- 管理 → 保存设置 → 历史数据优化：关闭自动读取，先预览再确认。后台暂缓新识别任务，等待当前附件结束后逐份迁移旧原件、移除可重建预览并清理无引用存储。缺少可重建原件的预览保留，原件校验异常时该份不优化。旧数据库不会在升级时自动重写。
- 默认勾选数据库整理（VACUUM）；需保守预留数据库文件两倍大小加磁盘保留空间。空间不足时保留已完成的去重和清理，显示未整理提示；可以释放空间后重新执行。整理期间不要关闭程序。中断的逐份迁移可重做，任务进度和最近 20 次记录本地保存。
- 新增统计区分数据库物理占用、识别结果、原件实际存储和临时预览缓存。仅删除内容不保证数据库立即缩小，必须完成整理才能回收物理文件空间。新版本读取仍兼容原内容列，无需重新导入邮件或重新 OCR。

### 诊断日志
邮件页面展开性能统计后，可导出最近3天或14天诊断日志 ZIP。Windows 本地日志目录为 `%LOCALAPPDATA%\FinanceReconciliation\logs`（自定义数据目录时跟随该目录）。单文件10MB，总上限100MB，保留14天；启动和每小时检查清理，写入时也检查限额。相同错误60秒内抑制重复记录，下次同类事件汇总重复次数。记录错误类型、AttributeError属性名、调用文件/行号及脱敏标识，不记录异常原文、正文、附件和密码；因此部分平台原始错误细节仍可能需要补充专项诊断。已有版本发生的错误不能追溯生成。


## 客户映射台账辅助匹配

收款匹配页可单独导入客户联系人台账（XLSX/CSV，最多5MB/20000行），与银行流水分开保存。表头支持 Customer Name、Customer Bank Name Reff、Email 或中文客户名称、银行付款人、邮箱；可指定工作表，默认第一个。联系电话和备注不用于身份推断。导入前将 Google 客户表导出为文件；本功能不会自动连接联系人在线表。

台账加密保存在本机，可停用或重新导入。无效文件不会替换旧台账；不完整行跳过并显示数量。完整邮箱精确对应，不按域名或发件人显示名猜客户。银行付款人和客户公司按规范化名称精确关联，不对台账做模糊扩散。

金额必须完全相同、币种已知且相同、日期满足原窗口时，映射才补充姓名分：缺失付款人且邮箱关系明确最多24分，明确公司别名22分，共享邮箱或一对多关系10分；与直接姓名分取较高值，不叠加超过30分。直接姓名完全匹配优先；已有明确无关付款人时不使用发件邮箱覆盖。台账不创建缺少金额/日期的虚构付款候选。

候选保留原始付款人，单独显示映射行号、公司、银行付款人和登记邮箱，并写入导出建议备注。映射修改或停用会重新计算候选及复核依赖该映射的确认；原证据未变化的直接姓名匹配确认保持。不会重新OCR、删除邮件、重置读取断点或自动确认关联。
